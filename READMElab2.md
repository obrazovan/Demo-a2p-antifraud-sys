# Лабораторная работа №2. Микросервисное приложение

## 1. Цель работы

Цель лабораторной работы — разработать полноценное backend-приложение на основе **микросервисной архитектуры**.

Необходимо самостоятельно спроектировать систему, разделив её функциональность на независимые backend-сервисы.

---

# 2. Основное требование

Приложение должно содержать **минимум 5–6 backend-микросервисов**.

> База данных, frontend/UI, API Gateway и reverse proxy не считаются полноценными бизнес-микросервисами.

То есть проект только с:

```text
Frontend
Backend
Database
```

не соответствует требованиям лабораторной работы.

---

# 3. Пример архитектуры

Допускается выбрать любую предметную область.

Например, система управления онлайн-магазином:

```text
                    ┌──────────────┐
                    │ API Gateway  │
                    └──────┬───────┘
                           │
        ┌──────────────────┼──────────────────┐
        │                  │                  │
        ▼                  ▼                  ▼
 ┌────────────┐     ┌────────────┐     ┌────────────┐
 │Auth Service│     │User Service│     │Product     │

        │                  │                  │
        └──────────────────┼──────────────────┘
                           │
             ┌─────────────┼─────────────┐

       │ Service  │  │ Service   │ │  Service  │
```

Это только пример.

Можно выбрать:

* систему мониторинга;
* игровой backend;
* собственную предметную область.

# 4. Требования к микросервисам

Каждый микросервис должен иметь:

* собственную ответственность;
* отдельный API;
* собственную бизнес-логику;
* возможность независимо запускаться;
* отдельную конфигурацию;
* обработку ошибок;
* logging.

Пример:

```text
User Service
    ↓
Работа с пользователями

Order Service
    ↓
Создание и управление заказами

Payment Service
    ↓
Платежи

Notification Service
    ↓
Отправка уведомлений
```

---

# 5. Независимость сервисов

Необходимо избегать архитектуры:

```text
Service A
   ↓
Service B
   ↓
Service C
   ↓
одна огромная Database
```

Микросервисы должны быть логически разделены.

Желательно использовать подход:

```text
Service A → Database A

Service B → Database B

Service C → Database C
```

Использование одной БД допускается только при наличии архитектурного обоснования.

---

# 6. Взаимодействие между сервисами

Необходимо реализовать взаимодействие между микросервисами.

Можно использовать:

### Синхронное взаимодействие

```text
REST
gRPC
```

### Асинхронное взаимодействие

```text
RabbitMQ
Kafka
NATS
Redis Streams
```

Желательно реализовать хотя бы один сценарий асинхронного взаимодействия.

Например:

```text
Order Service
      │
      │ OrderCreated
      ▼
   RabbitMQ
      │
      ▼
Notification Service
```

---

# 7. API Gateway

Рекомендуется использовать API Gateway.

Например:

```text
Client
  ↓
API Gateway
  ↓
┌────────────┬────────────┬────────────┐
│ Auth       │ User       │ Order      │
│ Service    │ Service    │ Service    │
└────────────┴────────────┴────────────┘
```

Gateway может отвечать за:

* routing;
* authentication;
* authorization;
* rate limiting;
* aggregation;
* logging.

# 9. Обязательные требования

В проекте должны присутствовать:

* минимум 5–6 backend-микросервисов;
* REST/gRPC API;
* взаимодействие между сервисами;
* база данных;
* обработка ошибок;
* logging;
* configuration management;
* authentication/authorization;
* документация API;
* health check endpoints.

Например:

```text
GET /health
GET /ready
```

---

# 10. Документация API

API должен быть документирован.

Для REST рекомендуется использовать:

* OpenAPI;
* Swagger UI.

В README необходимо показать основные endpoint'ы.

Пример:

```text
POST /api/auth/register
POST /api/auth/login

GET /api/users/{id}

GET /api/products
POST /api/products

POST /api/orders
GET /api/orders/{id}
```

---

# 11. Обработка ошибок

Необходимо корректно обрабатывать:

* неправильные входные данные;
* отсутствие ресурса;
* ошибки авторизации;
* ошибки внешних сервисов;
* timeout;
* ошибки базы данных.

Не рекомендуется возвращать пользователю stack trace.

---

# 12. Logging

Каждый сервис должен иметь logging.

Минимально необходимо логировать:

```text
Timestamp
Service
Log level
Request ID
Message
```

Желательно использовать структурированные логи:

```json
{
  "timestamp": "...",
  "service": "order-service",
  "level": "INFO",
  "request_id": "...",
  "message": "Order created"
}
```
